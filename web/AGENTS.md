# TinyTube — Agent Instructions

Kid-safe YouTube viewer. A child can only watch videos from parent-approved channels; there is deliberately **no search, no suggestions, no external navigation, and no backend**.

## Working style (owner's standing preferences)

- **Simplify aggressively.** The prime directive here: fewer files, fewer toolchains, less code. This repo went from Python-scraper + Makefile + 28 source files to one npm project with 8 flat source files — on purpose. Before adding a file, script, or dependency, ask whether an existing one can absorb the job. Prefer deleting over abstracting.
- **Never commit or push unless explicitly asked** ("commit", "push", `/shipit`).
- **Verify, don't assume.** Check claims empirically before acting on them: fetch the actual FA kit CSS to see which icons exist, run the downloader against the real API, run the suite after refactors. "Iterate till you make sure it works."
- Keep `README.md` tiny (badge + one setup line + run line); all detail lives here.
- Secrets via `.env` (gitignored) with a committed `.env.sample` naming the keys; anything needing a key must fail fast with copy-pasteable setup instructions, not a bare error.

## Architecture

Single top-level npm project (no Makefile, no Python): npm scripts are the only entry points, and the downloader is the webapp's own API client run under node.

```
channels.json ─▶ src/youtubeApi.js CLI (YouTube Data API, GH Actions cron) ─▶ public/videos.json ─▶ React SPA (GH Pages)
                                                                                                        │
                                                                                                 localStorage (watch history)
```

- `channels.json` — flat list: `[{channel, min_age?, max_age?}]`. `channel` may be a bare name (`JaredOwen` → `@JaredOwen`), `@handle`, `UC...` id, or full YouTube URL; ages default to 1/15. Prefer `UC...` ids: handles can be squatted by lookalike channels (the `@PeekabooKidz` handle belongs to a 1.6K-sub impostor of the 7.7M-sub real channel). When adding a channel, sanity-check the resolved subscriber count. The same flat `{channel, min_age, max_age}` shape is used in videos.json and in the settings localStorage model.
- `src/youtubeApi.js` — one file that is BOTH the webapp's Data API client (imported by settings/lib) AND the downloader CLI (`node src/youtubeApi.js`, guarded by an argv check; node builtins are lazily imported so vite never bundles them). Needs `YOUTUBE_API_KEY` (local: `.env`, loaded via `node --env-file-if-exists`; CI: repo secret). ~3 quota units per channel per run. `--seed` (the currently-deployed videos.json) is a per-channel stale fallback so one broken channel or API hiccup never blanks the site. Output `videos.json` (schema v2): `{schema_version, generated_at, channels: [{channel_id, channel_title, thumbnail, source_url, subscribers, video_count, view_count, made_for_kids, topics, min_age, max_age, videos: [{id,title,duration,thumbnail}]}]}`. Never commit `videos.json` or `.env` — both are gitignored.
- SPA — Vite + React 19 + Bootstrap 5 (CSS only) + react-youtube. Mobile-first (iPad/iPhone Safari), dark theme (the Android app's values-night palette: bg #0E1621, surface #182534, accent #7CC4FF — the red-to-accent remap lives at the bottom of styles.css; the player stays pure black), installable PWA (manifest + apple meta tags). Deliberately flat `src/`: one file per feature — `main.jsx` (App shell + boot), `landing.jsx` (enroll + math gates), `gallery.jsx`, `player.jsx`, `settings.jsx`, `lib.js` (all non-UI logic + hooks), `youtubeApi.js`, `styles.css` — plus `tests/*.test.js*`. Keep it that way; do not re-split into per-component files.
- Icons — owner's Font Awesome Pro token, loaded in `index.html` via the direct release URL (`ka-p.fontawesome.com/releases/v7.3.0/css/pro.min.css?token=a22be8527e`) rather than the kit CSS, which is pinned to 6.7.2 and lacks FA 7 icons like `fa-remote`. Before using an icon, confirm it exists in that CSS. House style is `fa-sharp-duotone fa-regular` for UI glyphs, `fa-duotone` for the tv-retro brand mark. The token serves ONLY the Pro/Brands/Duotone/Sharp/Sharp-Duotone fonts — new FA 7 families (`fa-utility-duo`, `fa-jelly-duo`) and the `fa-semibold` weight have no font files, so duo styles render their two layers as two side-by-side glyphs (verified empirically with the quota stopwatch).
- `public/` — every file is load-bearing for the install-as-app experience: `manifest.webmanifest` (`display: standalone`; deliberately NO `orientation` key — see player bullet), `icons/*.png` (Android install/splash + iOS apple-touch-icon; the FA kit cannot replace these — OS installers need real PNGs), and generated `videos.json`.

## npm scripts (the only entry points)

- `npm run download` — fetch channels via YouTube Data API → `public/videos.json`; fails fast with setup instructions if `YOUTUBE_API_KEY` is missing
- `npm run dev` — `predev` downloads videos.json if missing, then watch mode: vite dev server (`http://localhost:5173`; the `/TinyTube/` base path applies only to production builds) and vitest re-running affected tests on change, side by side via `concurrently`
- `npm test` — vitest suite (`tests/*.test.js*`: gallery sort logic + VideoPlayer lifecycle with a mocked react-youtube)
- `npm run prod` — download + test + `vite build` (CI runs the same steps individually; see deploy.yml)

## Key behaviors (do not regress)

- **Parent gate**: on a biometric-capable device, first load blocks on `EnrollGate` (`src/landing.jsx`) — nothing (not even the gallery) shows until a grown-up registers the device biometric (`src/lib.js` — serverless WebAuthn platform authenticator; Face ID/Touch ID/fingerprint via `userVerification: 'required'`, credential id in settings.passkeyId; a button because WebAuthn needs a user gesture). From then on the Parents button (gear, top right of gallery) triggers the OS biometric prompt directly; cancel/failed scan just returns to the gallery (no lockout mechanism). Devices WITHOUT a platform authenticator skip enrollment and protect parent mode with the `MathGate` (`src/landing.jsx`) 2-digit-addition gate (4 choices, 5-second countdown; wrong/timeout closes the gate). WebAuthn needs a secure context: localhost dev and the deployed HTTPS site work, LAN-IP dev URLs don't (those fall back to the math gate).
- **Settings** (parent-gated; `src/settings.jsx`): IMMEDIATE persistence — every valid change saves as it is made; there is no Save button and no draft. Rows holding half-typed values (BirthdayRow, the API key) buffer locally and commit only what parses. Age dual-slider (values on the thumbs); API-key row inside a real `<form>` with `autoComplete="current-password"` + hidden username so browser password managers offer to save the key; debounced (500ms, ≥3 chars — search.list costs 100 quota units; the follow-up channels.list enrichment is 1 unit and extra `part`s are free) autocomplete channel search whose result rows show the same stats/topics cells as the table; and the channel editor, which is a LIST rather than a table (no column headers, no columns to line up): each row is avatar, name, its stats beneath it unlabelled, an age chip with a pencil that opens the dual slider in a dialog, and a delete that confirms first. Channels in a group are drawn inside ONE block under the group's name — the group is the section a row sits in, not a column repeating that name on every row — arranged by the same `arrangeChannels` the child's Channels tab uses, so the two cannot disagree: grouped first (groups A-Z), then the channels this child can actually see, then A-Z. There is no enable checkbox: an approved channel is on, and a `disabled` left in an older blob is stripped on load rather than surviving as a state with no control to leave it. Everything fits a phone without a horizontal scroll, which is why the table (and @tanstack/react-table with it) went. Deleting curated = hidden flag, restorable. Rows sort descending by min then max age; the header shows an in-range counter (`Channel (8/10)`) and rows outside the global age filter gray out live. All via the **parent's own** Data API v3 key (stored locally; the deployed site ships no key — the CI `YOUTUBE_API_KEY` is build-time only). **This app stores the parent's DECISION; the Worker owns the FACTS.** `customChannels` rows are `{channel_id, min_age, max_age, disabled?}` and nothing else (`decisionOnly`, enforced on add, edit, import and on load, so older fat rows shrink) — the channel's name, avatar, stats and videos are the channel's own and change without anyone here doing anything. They come from the Worker's `/videos` shared cache in ONE batched request for every approved id (`getChannelsCached`, keyed on the ids alone so an age edit refetches nothing), and are joined back on by `hydrateChannel`, which falls back to the id so a channel whose record has not arrived is still listed and still removable. Works with NO api key; the parent's own key stays the per-channel fallback for videos. `seedChannelMeta` puts the name and avatar a search already showed on screen at add time. Everything the Worker sends is re-validated client-side — ids re-checked, avatars required to be https on a YouTube host, video thumbnails rebuilt from the id — because our own server saying so is not a reason to skip the check. The Worker refreshes its cache on its own daily cron (`wrangler.toml` `[triggers]`), so browsers rarely wait for a fetch. The header's top-right links the built commit (`__COMMIT_SHA__` via Vite define, from `git rev-parse HEAD`).
- **Age filter**: settings-driven — a channel shows when its `[min_age, max_age]` (curated value, or the parent's per-channel override) overlaps the EFFECTIVE range (inclusive); see `src/lib.js: effectiveAgeRange`. The parent PICKS the child's birthday from a dialog (a year to step through, twelve months to tap, future months not offered; stored `'YYYY-MM'`, born the 1st by declaration) and the age is computed live as a single-point range clamped to 1-15 — no stale age number. No birthday set falls back to the legacy `ageRange` (default 1-15, i.e. everything).
- **Kid-proof player** (`src/player.jsx`): www.youtube.com embed (NOT youtube-nocookie — it misfires as error 150 on mobile) with `controls:0, rel:0, fs:0, disablekb:1`; a transparent `TouchShield` swallows all touches; any non-playing state shows the opaque `PausedOverlay` so YouTube's "More videos" tray / end screen is never visible or tappable; ENDED → mark watched → back to gallery (no auto-advance).
- **Orientation**: gallery/settings always follow the device; ONLY the player forces landscape — `screen.orientation.lock` after fullscreen on Android, CSS 90° rotation fallback on iOS (`styles.css` portrait+coarse media query). Never put `orientation` in the manifest: installed PWAs honor it globally and lock every screen.
- **Video length** is a RANGE, not a floor: two thumbs on a 0…2h scale in 15-minute steps (values are shown BESIDE the setting's label, never inside the thumbs — two thumbs that meet printed their labels on top of each other; the slider sits on its own line below the label so it has the width to be dragged) (`LENGTH_STOPS`, the last stop being no ceiling at all), with "any" at both ends. The two may never meet — `clampLengthRange` keeps them a step apart, because a floor equal to its ceiling would hide everything but videos of exactly that length. A video with no known duration counts as very short at BOTH ends, so it is hidden by a floor and kept by a ceiling.
- **Watch quota is FOUR limits** (`QUOTA_PERIODS`): every 6 rolling hours, each day (midnight), each week (Sunday), each month (the 1st). Each is minutes or `null` for "no limit over this period" — which is not 0, and 0 still means no watching at all. A child watches under all of them at once and the TIGHTEST one stops them: `quotaState` returns how long is left, which period is binding, and that period's limit (the player's meter needs all three). Usage comes from the buckets that already existed — hours for the 6h window, days summed for week/month — via `statsUsage`, so the limits hold across synced devices. The pre-periods single `quotaMins` migrates onto `perDay`, the closest thing it meant. Edited in a DIALOG with a Save (`QuotaDialog`), whose thumbs show BARE MINUTES — "1h 15m" beside "1h" was two wide labels colliding whenever two thumbs came close, and a number is three characters at its worst — the one place in this app that does not persist as you type, because four half-edited limits are not a state worth keeping.
- **This week's override** (`week: {until, limits?, bonusMins?}`, `activeWeekOverride`): a grown-up can replace the limits for the current week (pencil on the red line in Settings — offering no MONTHLY limit, since a week cannot redraw a month; `setWeekLimits` carries the standing one through so an override can never quietly remove a cap) or grant +15/+30/+60 at the spent-quota screen, both gated by the same biometric parent mode uses (arithmetic fallback on a device with no lock — `main.jsx`'s `grant-gate` view). They are ONE object so setting limits does not drop granted minutes and vice versa. Both expire at the end of the week (`endOfWeek`, Sunday-based) and then stop existing — a change that quietly became permanent would be a parental control that erodes. Settings shows the override in RED, because a limit silently differing from the numbers on screen is the confusing kind. Everything that checks the cap reads `effectiveQuota`/`quotaState`, never the stored limits directly.
- **Watch quota** (`src/lib.js` quota section + `useWatchStore.usage`): parent-set cap (settings `quotaMins`, 0–240 in 15-min steps, default 180; 0 = no watching, there is deliberately no "off") on cumulative PLAYING seconds per **rolling 12h window** — the window starts at the first counted second and expires lazily on read (no timers). Only playing time counts: the player buffers seconds in a ref and flushes through the same save points as progress (every 5th playing tick, pause, hide, unmount). The player top bar shows "xx min remaining"; hitting zero mid-video hard-stops onto the `QuotaGate` screen (`src/landing.jsx`) — otherwise a video started with 1 min left would play out free. Gallery taps are checked at tap time (so lazy expiry unblocks immediately) and route to `QuotaGate`, whose Parents button reuses the same gate dispatch as the gallery's. Settings shows used-vs-quota as a fill on the quota slider (thumb label inside the thumb, h:mm) with a Session/24Hr/WTD/MTD/YTD stats table inline on the same row (hour buckets kept 48h for a true rolling 24Hr; day buckets kept 366 days; weeks start Sunday). There is deliberately no "reset usage" control: dragging the quota above what's used grants time, and the 12h expiry clears usage on its own.
- **Gallery sort** (`src/lib.js: gallerySort`): (1) in-progress 20–95% watched, closest-to-finish first; (2) unwatched, round-robin interleaved across channels so high-volume channels can't flood quiet ones; (3) abandoned <20%; (4) watched >95% last (the tail is usually credits).
- **Sync** (`src/lib.js` sync section + `SyncRow` in `src/settings.jsx`): cross-device state against the repo's Cloudflare Worker (`/sync/*` routes in the root `worker.js`, D1-backed), keyed by the parent's Google account. Sign-in is Google Identity Services (script loaded lazily, only from the parent-gated Settings), traded at `/sync/login` for a 90-day bearer session in `tinytube:sync:v1` `{token, email, expiresAt, deviceId, lastPushAt}`. Pull once per boot: watched merges row-wise last-write-wins by `updatedAt`; a newer remote settings blob replaces the local one KEEPING its remote `updatedAt` stamp (adopting is not an edit — `useSettings.update` only stamps when the patch carries no stamp). Push is debounced 5s: watched deltas since `lastPushAt`, the settings blob when its stamp moved, and this device's OWN usage buckets, always. Two invariants: pulled account-wide usage sums land in the watch store's `remote` field and are NEVER folded into `usage` (that would compound every device's totals each round trip), and quota checks use `usedSecs` = MAX(local 12h window, remote trailing-12h sum) — max, not sum, because the remote figure already contains this device's pushed buckets. The whole feature is inert (row hidden, zero network) while `GOOGLE_CLIENT_ID` in `lib.js` is empty. The synced settings blob includes the YouTube API key, by the owner's explicit choice.
- **Android parity (2026-08)**: the child side has a two-tab bottom bar (`gallery.jsx`) — Videos and a READ-ONLY Channels tab that narrows the grid to one channel or one group and can change nothing (curation edits live behind the parent gate). Channel GROUPS are ported from the Android app's ChannelGroups.kt (`lib.js` channelGroups section, `tests/channelGroups.test.js`): a group has >=2 members, under-two groups dissolve via `tidyGroups` after EVERY mutation, headers sort A-Z among themselves, and on the child's side a group's members are ALSO listed individually below its header. Groups live in settings (`groups` + `groupOf`) so they sync. The gallery toolbar's parent control is a worded "Parent" text button (the Android status bar's), not an icon; the grid is 2/3/4 columns per row. Channel management (search + table + grouping toolbar) is its own page inside Settings behind a "Manage channels" button; grouping selection uses the table's checkbox column, and the group-name dialog prefills/validates exactly as Android's does. Settings' header shows "Version N" (the pages deploy run number via `BUILD_VERSION` -> `__BUILD_VERSION__`), not a commit link.
- **Several children per account** (`src/lib.js` settings section): the stored blob is `{apiKey, passkeyId, children: [{id, name, ...CHILD_DEFAULTS}], activeChildId}` — a child owns their age/birthday, quota, min length, custom channels, overrides and groups; the household owns the API key and the parent's passkey. Everything that READS settings gets a FLATTENED view (account fields + the active child's, with `childId`/`childName` added), so no consumer knows about children at all; `storeApi`'s `update` vs `updateChild` is where the per-account/per-child line is drawn. Watch history and quota usage are per child too — one localStorage blob per child (`tinytube:v1:<childId>`), and `useWatchStore(childId)` swaps the whole history when the child changes. **The first child's id is the literal `default`**, not a UUID: the Worker migrates pre-children synced rows under that same id (`DEFAULT_CHILD`), so an account that was already syncing keeps its history — do not change either side alone. Add/switch/remove live in the header's three-dot menu and the name is edited at the top of Settings; the last child cannot be removed. The CHILD'S OWN status bar carries a picker too (left of the logo, only when there IS another child), behind the same gate as the Parent button beside it — choosing a child chooses a different set of approved channels.
- **Channel list import/export** (`lib.js`: `exportChannels` / `parseChannelImport`, menu items in `settings.jsx`'s `HeaderMenu`): a JSON file of ONE child's `customChannels` + `overrides` + `groups` + `groupOf`, so a parent can copy a setup to another child or another device. Import asks what to do: **Replace everything** (the file becomes the list, channels not in it go), **Merge — the file wins**, or **Merge — keep what is here**; the last two never remove a channel, and the who-wins pair only appears when the two lists actually disagree (`importConflicts`, `applyImport`). Merging joins groups BY NAME, so two lists that both call a shelf "Cartoons" end up with one — and the >=2-member rule is re-applied after, which can legitimately dissolve a group that a merge emptied. **Everything coming back in is re-validated** — the file is the one input a parent can hand this app from anywhere and it becomes what a child may watch: ids against `^UC[A-Za-z0-9_-]{22}$`, thumbnails against https + a YouTube image host (dropped, never the channel), ages clamped and inverted pairs swapped, override keys allow-listed, memberships pointing at absent groups dropped, and `tidyGroups` run so the >=2 rule holds. A recognised-but-empty file is fine; an unrecognised one throws a message a parent can read rather than silently emptying a grid.
- **localStorage** keys: `tinytube:v1:<childId>` per-child watch history (the bare `tinytube:v1` is the pre-children blob, adopted by the first child) `{lastVideoId, watched: {id: {pos, dur, completed, updatedAt}}, usage: {window: {start, secs}, days: {'YYYY-MM-DD': secs}, hours: {'<epochHour>': secs}}}` (watched LRU-capped 500, saved every 5 s while playing; usage feeds the quota + stats); `tinytube:settings:v1` parent settings `{apiKey, passkeyId, activeChildId, children: [{id, name, ageRange, birthday, quotaMins, minVideoMins, groups, groupOf, customChannels: [{channel_id, channel_title, thumbnail, min_age, max_age}], overrides: {channel_id: {min_age?, max_age?, hidden?}}}]}` (mirrors the flat channels.json shape; legacy hiddenChannels/ageOverrides/parentLockUntil fields are dropped or folded into `overrides` on load); `tinytube:videocache:v1` custom-channel video cache `{[channel_id]: {fetchedAt, videos}}` (24h TTL); `tinytube:sync:v1` the sync session (see the Sync bullet; the watch-history blob additionally carries a `remote` field with the account-wide usage sums from the last pull).

## Testing notes

- `tests/App.test.jsx` and `tests/MathGate.test.jsx` partially mock `src/lib.js` (`vi.mock` with `importOriginal` spread) because the gate functions share a module with hooks that must stay real — keep that pattern when adding mocks.
- `src/main.jsx` guards its `createRoot` on `#root` existing so tests can import `App` under jsdom; don't remove the guard.

## Deploy

`.github/workflows/deploy.yml`: push to `master` + daily cron + manual → npm ci / download (with `--seed` from the live site) / test / build → GitHub Pages (`https://pathikrit.github.io/TinyTube/`). Vite `base` comes from `BASE_PATH` env (defaults to `/TinyTube/`, build only). GitHub repo settings required once: Settings → Pages → Source = "GitHub Actions", and a `YOUTUBE_API_KEY` Actions secret for the downloader.
