# TinyTube — Agent Instructions

Kid-safe YouTube viewer. A child can only watch videos from parent-approved channels; there is deliberately **no child-facing search, no suggestions, no external navigation, and no built-in catalog**.

## Working style (owner's standing preferences)

- **Simplify aggressively.** The prime directive here: fewer files, fewer toolchains, less code. This repo went from Python-scraper + Makefile + 28 source files to one npm project with 8 flat source files — on purpose. Before adding a file, script, or dependency, ask whether an existing one can absorb the job. Prefer deleting over abstracting.
- **Never commit or push unless explicitly asked** ("commit", "push", `/shipit`).
- **Verify, don't assume.** Check claims empirically before acting on them: fetch the actual FA kit CSS to see which icons exist, hit the Worker when changing `/videos` or `/channel`, run the suite after refactors. "Iterate till you make sure it works."
- Keep `README.md` tiny (badge + one setup line + run line); all detail lives here.
- Secrets via `.env` (gitignored) with a committed `.env.sample` naming the keys; anything needing a key must fail fast with copy-pasteable setup instructions, not a bare error.

## Architecture

Single top-level npm project (no Makefile, no Python): npm scripts are the only entry points.

```
Parent-approved channel ids ─▶ Worker /videos (shared D1 cache) ─▶ React SPA (GH Pages)
                                                                          │
                                                                   localStorage (watch history)
```

There is no built-in catalog. The grid is whatever the parent approved (search on the Channels tab); an empty approved list is an empty grid. Channel titles, avatars and videos come from the Worker's `/videos` cache, not from a file this app ships.
- `src/youtubeApi.js` — the webapp's YouTube client: Worker `/videos`, `/channel` and `/search` (no key), plus an optional parent Data API v3 key as a fallback for fetching videos if the Worker's cache is down. Needs no key at build time. Never commit `.env`.
- SPA — Vite + React 19 + Bootstrap 5 (CSS only) + react-youtube. Mobile-first (iPad/iPhone Safari), dark theme (the Android app's values-night palette: bg #0E1621, surface #182534, accent #7CC4FF — the red-to-accent remap lives at the bottom of styles.css; the player stays pure black), installable PWA (manifest + apple meta tags). Deliberately flat `src/`: one file per feature — `main.jsx` (App shell + boot), `landing.jsx` (enroll + math gates), `gallery.jsx`, `player.jsx`, `settings.jsx`, `lib.js` (all non-UI logic + hooks), `youtubeApi.js`, `styles.css` — plus `tests/*.test.js*`. Keep it that way; do not re-split into per-component files.
- Icons — owner's Font Awesome Pro token, loaded in `index.html` via the direct release URL (`ka-p.fontawesome.com/releases/v7.3.0/css/pro.min.css?token=a22be8527e`) rather than the kit CSS, which is pinned to 6.7.2 and lacks FA 7 icons like `fa-remote`. Before using an icon, confirm it exists in that CSS. House style is `fa-sharp-duotone fa-regular` for UI glyphs, `fa-duotone` for the tv-retro brand mark. The token serves ONLY the Pro/Brands/Duotone/Sharp/Sharp-Duotone fonts — new FA 7 families (`fa-utility-duo`, `fa-jelly-duo`) and the `fa-semibold` weight have no font files, so duo styles render their two layers as two side-by-side glyphs (verified empirically with the quota stopwatch).
- `public/` — every file is load-bearing for the install-as-app experience: `manifest.webmanifest` (`display: standalone`; deliberately NO `orientation` key — see player bullet), `icons/*.png` (Android install/splash + iOS apple-touch-icon; the FA kit cannot replace these — OS installers need real PNGs).

## npm scripts (the only entry points)

- `npm run dev` — watch mode: vite dev server (`http://localhost:5173`; the `/TinyTube/` base path applies only to production builds) and vitest re-running affected tests on change, side by side via `concurrently`
- `npm test` — vitest suite (`tests/*.test.js*`: gallery sort logic + VideoPlayer lifecycle with a mocked react-youtube)
- `npm run prod` — test + `vite build` (CI runs the same steps individually; see `.github/workflows/pages.yml`)

## Key behaviors (do not regress)

- **Parent gate**: on a biometric-capable device, first load blocks on `EnrollGate` (`src/landing.jsx`) — nothing (not even the gallery) shows until a grown-up registers the device biometric (`src/lib.js` — serverless WebAuthn platform authenticator; Face ID/Touch ID/fingerprint via `userVerification: 'required'`, credential id in settings.passkeyId; a button because WebAuthn needs a user gesture). From then on the Parents button (gear, top right of gallery) triggers the OS biometric prompt directly; cancel/failed scan just returns to the gallery (no lockout mechanism). Devices WITHOUT a platform authenticator skip enrollment and protect parent mode with the `MathGate` (`src/landing.jsx`) 2-digit-addition gate (4 choices, 5-second countdown; wrong/timeout closes the gate). WebAuthn needs a secure context: localhost dev and the deployed HTTPS site work, LAN-IP dev URLs don't (those fall back to the math gate).
- **Settings** (parent-gated; `src/settings.jsx`): IMMEDIATE persistence — every valid change saves as it is made; there is no Save button and no draft. Rows holding half-typed values (BirthdayRow, the API key) buffer locally and commit only what parses. Age dual-slider (values on the thumbs); API-key row inside a real `<form>` with `autoComplete="current-password"` + hidden username so browser password managers offer to save the key; debounced (500ms, ≥3 chars) autocomplete channel search on the Channels tab (Worker `/search` for a name, `/channel` for a URL or @handle — no parent API key); result rows show the same stats/topics cells as the table when those are known; and the channel editor, which is a LIST rather than a table (no column headers, no columns to line up): each row is avatar, name, its stats beneath it unlabelled, an age chip with a pencil that opens the dual slider in a dialog, and a delete that confirms first. Channels in a group are drawn inside ONE block under the group's name — the group is the section a row sits in, not a column repeating that name on every row — arranged by the same `arrangeChannels` the child's Channels tab uses, so the two cannot disagree: grouped first (groups A-Z), then the channels this child can actually see, then A-Z. There is no enable checkbox: an approved channel is on, and a `disabled` left in an older blob is stripped on load rather than surviving as a state with no control to leave it. Everything fits a phone without a horizontal scroll, which is why the table (and @tanstack/react-table with it) went. Rows sort descending by min then max age; the header shows an in-range counter (`Channel (8/10)`) and rows outside the global age filter gray out live. Search and paste go through the Worker (`/search`, `/channel`) with no parent API key. The optional Data API v3 key in Settings is only a fallback for fetching videos if the Worker's cache is down. **This app stores the parent's DECISION; the Worker owns the FACTS.** `customChannels` rows are `{channel_id, min_age, max_age}` and nothing else (`decisionOnly`, enforced on add, edit, import and on load, so older fat rows shrink) — the channel's name, avatar, stats and videos are the channel's own and change without anyone here doing anything. They come from the Worker's `/videos` shared cache in ONE batched request for every approved id (`getChannelsCached`, keyed on the ids alone so an age edit refetches nothing), and are joined back on by `hydrateChannel`, which falls back to the id so a channel whose record has not arrived is still listed and still removable. Works with NO api key; the parent's own key stays the per-channel fallback for videos. `cacheResolvedChannel` writes the name, avatar and any videos a search already returned before the parent closes Parents Mode. Everything the Worker sends is re-validated client-side — ids re-checked, avatars required to be https on a YouTube host, video thumbnails rebuilt from the id — because our own server saying so is not a reason to skip the check. The Worker refreshes its cache on its own daily cron (`wrangler.toml` `[triggers]`), so browsers rarely wait for a fetch. The header's top-right links the built commit (`__COMMIT_SHA__` via Vite define, from `git rev-parse HEAD`).
- **Age filter**: settings-driven — a channel shows when its `[min_age, max_age]` overlaps the EFFECTIVE range (inclusive); see `src/lib.js: effectiveAgeRange`. Either bound may be `null` for “any”. The dual slider’s stops are **any | 1 … 14 | any** (new channels default to any–any). The parent PICKS the child's birthday from a dialog (a year to step through, twelve months to tap, future months not offered; stored `'YYYY-MM'`, born the 1st by declaration) and the age is computed live as a single-point range floored at 1 but **not capped at 14** — a 15-year-old must miss a 1–14 channel and still match `any`. No birthday set falls back to the legacy `ageRange` (default 1-15, i.e. everything). The old stored 1–15 “everything” migrates to any–any; a leftover `max_age` of 15 becomes `null`.
- **Kid-proof player** (`src/player.jsx`): www.youtube.com embed (NOT youtube-nocookie — it misfires as error 150 on mobile) with `controls:0, rel:0, fs:0, disablekb:1`; a transparent `TouchShield` swallows all touches; any non-playing state shows the opaque `PausedOverlay` so YouTube's "More videos" tray / end screen is never visible or tappable; ENDED → mark watched → tell the CALLER (`onEnded`), which is what auto-advance hangs off — with no `onEnded` a finished video still just returns to the gallery.
- **Orientation**: gallery/settings always follow the device; ONLY the player forces landscape — `screen.orientation.lock` after fullscreen on Android, CSS 90° rotation fallback on iOS (`styles.css` portrait+coarse media query). Never put `orientation` in the manifest: installed PWAs honor it globally and lock every screen.
- **Watch quota is FOUR limits** (`QUOTA_PERIODS`): every 6 rolling hours, each day (midnight), each week (Sunday), each month (the 1st). Each is minutes or `null` for "no limit over this period" — which is not 0, and 0 still means no watching at all. A child watches under all of them at once and the TIGHTEST one stops them: `quotaState` returns how long is left, which period is binding, and that period's limit (the player's meter needs all three). Usage comes from the buckets that already existed — hours for the 6h window, days summed for week/month — via `statsUsage`, so the limits hold across synced devices. The pre-periods single `quotaMins` migrates onto `perDay`, the closest thing it meant. Each period's scale reaches ALMOST its own length and stops one step short (`lastFiniteLimit`), because a cap equal to the window it governs forbids nothing — six hours inside a rolling six hours was "no limit" wearing a number, and "no limit" is the stop past the end. Steps are what is worth dragging at that size (15m / 1h / half a day / 1 day, all dividing evenly, none more than 48 stops), and a period may name its own unit — the week and the month count in DAYS (`limitLabel`, halves included), the shorter ones in `shortDuration`'s single token. The SAME function draws the thumb and the line above it: they disagreed once, "2d" over "48h" for one value, and a settings screen that contradicts itself is worse than a terse one; a stored value that reaches its period is normalized to null on load and on save (`normalizeQuota`). Edited in a DIALOG with a Save (`QuotaDialog`), whose thumbs show ONE TOKEN (`shortDuration`: bare minutes under an hour, then `3h`, then `2d`) — "1h 15m" beside "1h" was two wide labels colliding whenever two thumbs came close — the one place in this app that does not persist as you type, because four half-edited limits are not a state worth keeping.
- **Today's override** (`day: {until, limits?, bonusMins?}`, `activeDayOverride`): a grown-up can replace the limits for TODAY (pencil on the red line in Settings — offering only the 6-hour and daily periods, since a day cannot redraw a week or a month; `setDayLimits` carries the standing longer caps through so an override can never quietly remove one) or grant +15/+30/+60 at the spent-quota screen, both gated by the same biometric parent mode uses (arithmetic fallback on a device with no lock — `main.jsx`'s `grant-gate` view). They are ONE object so setting limits does not drop granted minutes and vice versa. Both die at MIDNIGHT (`endOfDay`) and then stop existing — an exception that outlived the evening it was made for would be a parental control that erodes, and a week is far too long to owe a decision taken at one bedtime. Settings shows the override in RED, because a limit silently differing from the numbers on screen is the confusing kind. Everything that checks the cap reads `effectiveQuota`/`quotaState`, never the stored limits directly.
- **Gallery sort** (`src/lib.js: gallerySort`): (1) in-progress 20–90% watched, closest-to-finish first; (2) unwatched, round-robin interleaved across channels so high-volume channels can't flood quiet ones; (3) abandoned <20%; (4) watched last (the tail is usually credits). **Watched is ONE number, `WATCHED_THRESHOLD` = 0.9, and strictly above it** — the badge on a card, the bucket that sinks, what `hideWatched` hides and what `saveProgress` latches as `completed` all read that one constant, so they cannot disagree; exactly 90% is still something to finish. The parent's **Hide Watched** switch (per child) drops that bucket off the grid entirely rather than sinking it; off by default, because a child re-watching a favourite is not a problem to solve.
- **What plays next** (`src/lib.js: nextIndex`/`playbackMode`, the parent's **Play Next** setting): the Android app's `Playlist.kt` ported case for case, tests included (`tests/playback.test.js` ← `PlaylistTest.kt`). `IN_ORDER` walks down the grid and STOPS at the end rather than wrapping; `RANDOM` never repeats the video that just played, reaches every other one from exactly one roll, and gives up below two videos. **`RANDOM` also PREFERS what has not been watched** — the one place this diverges from `Playlist.kt`, which knows only a count and an index: random over everything kept handing repeats to a child who had seen most of a channel, the complaint random was meant to answer. The pool narrows to the unwatched and falls back to every other video when there are none, because a preference must not stop playback; watched means `WATCHED_THRESHOLD`, the same number as the badge and the sort, read through `nextVideoIndex` off the store the grid uses. With `hideWatched` on this changes nothing — those videos never reach the list. `playback.test.js` carries an equivalence case proving that with nothing known about watching, every roll still gives the Kotlin answer, so the divergence is an addition rather than a drift. `roll` is injected so the random half is pinned rather than sampled, and it is floored and clamped (NaN included — `Math.min`/`Math.max` pass NaN straight through) because it is the one input from outside. **The list is whatever the child tapped on**: `Gallery`'s `onPlay(list, index)` hands over the whole visible, already-sorted grid and `App` holds it as `{list, index}`, so a video started from a channel-filtered grid cannot lead out of that channel — and there is no rule in the player saying so. `VideoPlayer` is keyed on the video id, so an advance remounts it rather than swapping a video in under refs that describe the last one. It lives above `CHILD_DEFAULTS` in `lib.js`, not beside the gallery sort it serves, because the defaults name the mode and a `const` cannot be read before it is declared.
- **Sync** (`src/lib.js` sync section + `SyncRow` in `src/settings.jsx`): cross-device state against the repo's Cloudflare Worker (`/sync/*` routes in the root `worker.js`, D1-backed), keyed by the parent's Google account. Sign-in is Google Identity Services (script loaded lazily, only from the parent-gated Settings), traded at `/sync/login` for a 90-day bearer session in `tinytube:sync:v1` `{token, email, expiresAt, deviceId, lastPushAt}`. Pull on boot, on a child switch, on every playback and from the header's Refresh button, throttled to `PULL_MIN_MS` (15 min) — except when the quota is spent, where the tap FORCES one past the throttle and awaits it, because a grown-up may have granted time from another device and that grant is in the settings blob. A failed pull does not spend the window. Watched merges row-wise last-write-wins by `updatedAt`; a newer remote settings blob replaces the local one KEEPING its remote `updatedAt` stamp (adopting is not an edit — `useSettings.update` only stamps when the patch carries no stamp). Push is debounced 5s: watched deltas since `lastPushAt`, the settings blob when its stamp moved, and this device's OWN RECENT usage buckets, always — `usagePushDelta`: the trailing 6 hours (exactly the window `per6h` reads) plus TODAY's day bucket, and nothing else. A device is an authority on its own recent watching; week/month/year are summed out of D1 across every device on the pull, so re-sending them was ~416 rows of settled history every few seconds. Today's day bucket goes up even though the hours could add up to it, because the day key is LOCAL and an hour key is an epoch hour — the Worker cannot derive one from the other without the device's timezone. A device's FIRST push carries everything it has, since a phone used offline and then signed in owes the account that history and nothing else will carry it. Two invariants: pulled account-wide usage sums land in the watch store's `remote` field and are NEVER folded into `usage` (that would compound every device's totals each round trip), and quota checks use `usedSecs` = MAX(local 12h window, remote trailing-12h sum) — max, not sum, because the remote figure already contains this device's pushed buckets. The whole feature is inert (row hidden, zero network) while `GOOGLE_CLIENT_ID` in `lib.js` is empty. The synced settings blob includes the YouTube API key, by the owner's explicit choice.
- **Android parity (2026-08)**: the child side has a two-tab bottom bar (`gallery.jsx`) — Videos and a READ-ONLY Channels tab that narrows the grid to one channel or one group and can change nothing (curation edits live behind the parent gate). Channel GROUPS are ported from the Android app's ChannelGroups.kt (`lib.js` channelGroups section, `tests/channelGroups.test.js`): a group has >=2 members, under-two groups dissolve via `tidyGroups` after EVERY mutation, headers sort A-Z among themselves, and on the child's side a group's members are ALSO listed individually below its header. Groups live in settings (`groups` + `groupOf`) so they sync. The gallery toolbar's parent control is a worded "Parent" text button (the Android status bar's), not an icon; the grid is 2/3/4 columns per row. Channel management (search + table + grouping toolbar) is its own page inside Settings behind a "Manage channels" button; grouping selection uses the table's checkbox column, and the group-name dialog prefills/validates exactly as Android's does. Settings' header shows "Version N" (the pages deploy run number via `BUILD_VERSION` -> `__BUILD_VERSION__`), not a commit link.
- **Who may change the parent's controls** (`src/lib.js: settingsLock`, `normEmail`): Parents Mode is EDITABLE only when a grown-up is signed in — every tab is wrapped in a `<fieldset disabled>` plus a `pointer-events:none` class (the two sliders are dragged by a plain div a disabled fieldset cannot reach), with a banner saying which of the two locks applies. It locks when a CHILD is signed in (their `email`, an optional per-child field under Name, matches the session — compared through `normEmail`, so case and spaces cannot make the lock miss) and when NOBODY is signed in, because settings anyone can open on an unclaimed device are not a parental control. **The sign-in control stays live inside a locked screen**, deliberately outside the fieldset: signing in is the only way out of either state, so burying it inside what the lock disables would make the lock permanent. Two more escapes are load-bearing. A build with no `GOOGLE_CLIENT_ID` cannot sign in at all, so it does not lock either — sync is inert there and so is this. And setting a child's email to the address the PARENT is signed in with is REFUSED rather than warned about: it locks immediately, and sign-out lands on the signed-out lock while signing back in lands on the child lock, so there is no route back from inside the app. This is a UI lock over localStorage, not a security boundary — it stops a child using the controls, not one who can open devtools.
- **Several children per account** (`src/lib.js` settings section): the stored blob is `{apiKey, passkeyId, children: [{id, name, ...CHILD_DEFAULTS}], activeChildId}` — a child owns their age/birthday, their own email (see the lock bullet above), quota, hide-watched switch, play-next mode, custom channels, overrides and groups; the household owns the API key and the parent's passkey. Everything that READS settings gets a FLATTENED view (account fields + the active child's, with `childId`/`childName` added), so no consumer knows about children at all; `storeApi`'s `update` vs `updateChild` is where the per-account/per-child line is drawn. Watch history and quota usage are per child too — one localStorage blob per child (`tinytube:v1:<childId>`), and `useWatchStore(childId)` swaps the whole history when the child changes. **The first child's id is the literal `default`**, not a UUID: the Worker migrates pre-children synced rows under that same id (`DEFAULT_CHILD`), so an account that was already syncing keeps its history — do not change either side alone. Add/switch/remove live in the header's three-dot menu and the name is edited at the top of Settings; the last child cannot be removed. The CHILD'S OWN status bar carries a picker too (left of the logo, only when there IS another child), behind the same gate as the Parent button beside it — choosing a child chooses a different set of approved channels.
- **Channel list import/export** (`lib.js`: `exportChannels` / `parseChannelImport`, menu items in `settings.jsx`'s `HeaderMenu`): a JSON file of ONE child's `customChannels` + `overrides` + `groups` + `groupOf`, so a parent can copy a setup to another child or another device. Import and export are the ACTIVE CHILD's alone — the menu names them ("Bob's channels") and both read and write through the flattened view, so another child's list is never in the file and never touched by one. Import asks what to do: **Replace everything** (the file becomes the list, channels not in it go), **Merge — the file wins**, or **Merge — keep what is here**; the last two never remove a channel, and the who-wins pair only appears when the two lists actually disagree (`importConflicts`, `applyImport`). Merging joins groups BY NAME, so two lists that both call a shelf "Cartoons" end up with one — and the >=2-member rule is re-applied after, which can legitimately dissolve a group that a merge emptied. **Everything coming back in is re-validated** — the file is the one input a parent can hand this app from anywhere and it becomes what a child may watch: ids against `^UC[A-Za-z0-9_-]{22}$`, thumbnails against https + a YouTube image host (dropped, never the channel), ages clamped and inverted pairs swapped, override keys allow-listed, memberships pointing at absent groups dropped, and `tidyGroups` run so the >=2 rule holds. A recognised-but-empty file is fine; an unrecognised one throws a message a parent can read rather than silently emptying a grid.
- **localStorage** keys: `tinytube:v1:<childId>` per-child watch history (the bare `tinytube:v1` is the pre-children blob, adopted by the first child) `{lastVideoId, watched: {id: {pos, dur, completed, updatedAt}}, usage: {window: {start, secs}, days: {'YYYY-MM-DD': secs}, hours: {'<epochHour>': secs}}}` (watched LRU-capped 500, saved every 5 s while playing; usage feeds the quota + stats); `tinytube:settings:v1` parent settings `{apiKey, passkeyId, activeChildId, children: [{id, name, ageRange, birthday, quotaMins, groups, groupOf, customChannels: [{channel_id, min_age, max_age}], overrides: {}}]}` (legacy hiddenChannels/ageOverrides/parentLockUntil/`hidden`/`disabled`/`minVideoMins`/`maxVideoMins` fields are dropped or folded on load); `tinytube:videocache:v1` custom-channel video cache `{[channel_id]: {fetchedAt, videos}}` (24h TTL); `tinytube:sync:v1` the sync session (see the Sync bullet; the watch-history blob additionally carries a `remote` field with the account-wide usage sums from the last pull).

## Testing notes

- `tests/App.test.jsx` and `tests/MathGate.test.jsx` partially mock `src/lib.js` (`vi.mock` with `importOriginal` spread) because the gate functions share a module with hooks that must stay real — keep that pattern when adding mocks.
- `src/main.jsx` guards its `createRoot` on `#root` existing so tests can import `App` under jsdom; don't remove the guard.

## Deploy

`.github/workflows/pages.yml`: push to `main` (path-filtered to `web/**`) + auto-merge dispatch + manual → npm ci / test / build → GitHub Pages (`https://vtlinh.github.io/tinytube/`). Vite `base` comes from `BASE_PATH` env (defaults to `/TinyTube/` in this copy; the workflow sets `/tinytube/`). GitHub repo settings required once: Settings → Pages → Source = "GitHub Actions". No YouTube API key is needed to build or deploy.
